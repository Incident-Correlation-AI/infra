# Change 01 — Frontend deploys to Vercel

> **Date:** 2026-10-22 · **Status:** Accepted · **Owner:** LAD (infra lane)
> **Replaces:** "web/dashboard hosted on Render" plan discussed informally.

## What changed

The web dashboard is planned and deployed **as if it will live on Vercel**. Any
previously imagined Render-based hosting of the dashboard (or a Render-hosted
backend on a "free plan") is dropped from this project's lane.

## Why (reasons)

| # | Reason | Detail |
|---|---|---|
| R1 | **The docs leave the host open on purpose** | `03_CLOUD_AND_BACKEND_GUIDE.md` marks static hosting as *optional* (`Step 4.9`), suggesting S3+CloudFront as an example, not a requirement. Only one constraint exists: the API's CORS allow-list must contain the deployed origin (never `*`). Vercel satisfies it identically. |
| R2 | **The dashboard is a pure SPA** | React + Vite builds to static assets that call the Incident API over HTTPS. No server-side rendering, no background jobs, no state worth keeping on the host — so there is nothing a Render service (process-based) would add over a static host. |
| R3 | **Better fit for frontend delivery** | Free tier, automatic preview deploys per PR, instant rollbacks, CDN edge caching. For a dashboard that changes frequently during development, preview links beat container/instance deploys. |
| R4 | **Cost and surface discipline** | Zero running servers to pay for or keep awake. The only "production" runtime in this project remains the AWS serverless lane (API GW + Lambdas), which we already own and verified end-to-end. |

## What stays the same

- **The backend stays AWS** — API Gateway (`d6l60no0kk…`) + Ingest/Worker/Read/Authorizer
  Lambdas + SQS/DLQ + DynamoDB. The site renders data; it does *not* become a backend.
- Collectors still POST to `POST /api/v1/events/batch` with the collector token;
  the dashboard calls `/api/v1/incidents*` with the admin token. Nothing in the
  API contract moves with this change.
- The twin-mode promise (`src/lad/` same core in local mode and AWS mode) is
  untouched. Vercel vs Render was never part of that decision.

## Actions triggered by this change

1. **After the dashboard deploys to Vercel**, add the production origin to the
   API's CORS allow-list (currently `http://localhost:5173` + `:3000`), e.g.:

   ```bash
   aws apigatewayv2 update-api \
     --region eu-north-1 --api-id d6l60no0kk \
     --cors-config ... # add https://<final-app>.vercel.app
   ```

   (Execute via the same API-managed flow used in the audit passes; verify with
   an OPTIONS preflight returning 204 from the deployed origin.)

2. Record the decision here as **D-006 (frontend on any static host; chosen: Vercel)**.
3. Dashboards/users must never hold AWS keys or tokens beyond the admin token
   the API contract already allows (`03_…GUIDE.md`, C6). Vercel env vars must not
   contain secrets beyond what the SPA needs at runtime.
